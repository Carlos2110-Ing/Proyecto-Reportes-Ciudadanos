## 1. INFORMACIÓN GENERAL

Nombre del proyecto:
SafePeru

Nombre completo:
Sistema de Reportes Ciudadanos

Tipo de proyecto:
Proyecto académico de desarrollo web.

Objetivo principal:
Crear una plataforma web que permita a los ciudadanos registrar,
consultar y gestionar reportes relacionados con problemas o incidentes
que ocurren en su entorno, facilitando la participación ciudadana y
la comunicación mediante un sistema organizado de reportes.

Idea principal:
SafePeru busca funcionar como un puente tecnológico entre los
ciudadanos y la gestión de incidencias de una comunidad.

El sistema permite registrar situaciones como:

* Problemas de infraestructura.
* Situaciones de seguridad.
* Problemas ambientales.
* Problemas de tránsito.
* Emergencias u otros incidentes ciudadanos.

IMPORTANTE:
SafePeru es un proyecto académico/prototipo. No debe presentarse como
una plataforma oficial del Estado peruano ni como un sistema conectado
realmente con municipalidades o autoridades gubernamentales.

* Manejar roles.

# ============================================================
# 6. ROLES Y PERMISOS
# ============================================================

SafePeru utiliza un sistema de roles y permisos.

La idea es que el acceso no dependa únicamente de ocultar botones
en el frontend.

La seguridad debe validarse también en el backend.

Ejemplos de rutas:

/login
/registro
/dashboard
/perfil
/admin

Las rutas públicas deben poder utilizarse sin autenticación.

Las rutas privadas requieren una sesión/autenticación válida.

Las rutas administrativas requieren los permisos correspondientes.

# ============================================================
# 14. FRONTEND
# ============================================================

Reglas importantes:

1. Mantener HTML, CSS y JavaScript separados cuando sea posible.

2. Evitar estilos inline como:

style="color: red;"

Preferir clases CSS:

class="mi-elemento"

3. Reutilizar variables CSS existentes.

4. Mantener Bootstrap para layout y responsive.

5. Utilizar Font Awesome y Bootstrap Icons cuando corresponda.

6. No introducir otra librería visual sin necesidad.

7. Mantener compatibilidad responsive.

8. Los botones deben tener estados visuales claros.

9. Los formularios deben mostrar validaciones comprensibles.

10. Las animaciones deben ser rápidas y discretas.

# ============================================================
# 16. MANEJO DE ERRORES
# ============================================================

El sistema contempla excepciones específicas para situaciones como:

* Recurso no encontrado.
* Solicitud inválida.
* Conflicto.
* Datos duplicados.
* Errores de validación.

Ejemplo:

Si se intenta registrar un correo que ya existe:

HTTP:
409 Conflict

La respuesta debe contener un mensaje entendible.

No mostrar stack traces al usuario final.

# ============================================================
# 18. VALIDACIONES
# ============================================================

Los datos recibidos deben validarse antes de procesarlos.

Ejemplos:

Correo:
Debe tener un formato válido.

Contraseña:
Debe cumplir las reglas definidas por el sistema.

Campos obligatorios:
No deben aceptar valores nulos cuando el negocio no lo permita.

IMPORTANTE:
Hay una diferencia entre:

null

y

false

Para campos booleanos primitivos, Jackson puede producir errores
si recibe null.

Cuando se permita un valor opcional, evaluar utilizar Boolean en
lugar de boolean o establecer una estrategia adecuada de
deserialización.

# ============================================================
# 19. PERSISTENCIA JSON
# ============================================================

En la etapa basada en JSON, los datos se almacenan en un archivo general.

Ejemplos:

db.json

El repositorio genérico permite trabajar con diferentes entidades.

IMPORTANTE:
Verificar siempre la ruta configurada de los archivos.

Ejemplo:

app.data=...

No asumir que la carpeta data está necesariamente dentro de
src/main/resources.
